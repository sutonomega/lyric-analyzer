# Ollamaの起動・停止・再起動（2026-11-18）

利用者からの接続失敗、画面内からの起動、アプリ終了時の停止、異常終了後の再起動の要望に対応した。Issue #11の候補生成を利用可能にする操作の追加であり、候補品質の評価は継続する。

- Windowsのインストール済み `ollama.exe` を探し、引数を分けて `serve` を非表示で起動。固定のループバック接続、クラウド無効、要求ログ無効を指定する。自動インストール・モデル取得・歌詞生成はしない。
- 応答するサービスが既にあれば二重起動しない。応答待ちや不明な返答の場合も追加起動しない。起動が遅い場合はモデル確認操作へ案内する。
- アプリが起動したプロセスをWindows Job Objectの `KILL_ON_JOB_CLOSE` で管理する。通常の終了処理と、強制終了時のOSによるハンドル解放の両方で、所属するOllamaと子プロセスを停止する。ブラウザーのタブ終了はバックエンド終了ではない。
- 明示的な停止・再起動では、外部起動の対象も固定ポートの所有者・実行ファイル名・serve引数を照合する。全ollamaプロセスを一括停止しない。自動終了時は外部起動を停止しない。
- WSL・Docker等の転送プロセスはWindows版Ollamaと確認できないため操作を拒否する。起動元での停止・再起動を案内する。
- 接続不能、待ち時間超過、HTTPエラー、返答形式エラーを分け、保存失敗時の二重の句点も修正した。

## 確認

全415テスト、型チェック、差分チェックが成功した。起動済み時の重複防止、応答不明時の起動中止、停止済みからの再起動、管理登録失敗時の後始末、未知の接続先の停止拒否、確認したPIDだけの停止、Windows Jobの実プロセス終了、画面操作時に生成や分析履歴の変更をしないことを検証した。

実際のStreamlitを専用データ保存先・8765ポートで動かし、agent APIから起動・停止・起動・再起動を操作した。Windows版Ollamaだけを別ポート11435に接続する検証用の起動処理へ差し替え、通常のサービス管理と画面処理を使用した。対象PIDを終了して異常終了を再現した後、再起動できること、バックエンドの強制終了で管理対象が停止することを確認した。モデル一覧のみを取得し、候補生成は実行していない。実歌詞と利用者DBは使用していない。コンソールに追加の警告・例外はなかった。

既存の11434接続はWSL転送だったため、停止要求を安全に拒否することを確認した。そのサービスはそのまま利用可能で、検証用の画面と11435サービスは終了済み。実環境でのWindows版の外部起動サービスの停止は、PID照合の単体検証のみであり、WSLの停止を代替したとは扱わない。

Windowsの終了連動の根拠：[Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)。
