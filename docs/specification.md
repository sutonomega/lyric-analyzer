## 1. 目的と判断原則

新しい歌詞を過去曲と比較し、繰り返し使う語句と定型的な表現を、根拠となる行とともに提示する。修正は利用者が選ぶ。「AIらしさ」は作者や生成元の判定ではなく、登録した表現ルールに該当することを意味する。独自性の点数やAI生成確率は出さない。

過去曲での頻出度と定型表現への該当は別々に表示する。両方に該当した箇所を優先表示するが、一方だけの指摘も残す。

## 2. MVPの範囲

| 機能 | MVPの動作 |
| --- | --- |
| 楽曲管理 | 曲名・歌詞・テーマ・タグを登録、編集、削除、検索。編集時は改訂を作る |
| 分析 | 未保存の歌詞も解析。比較対象曲と期間を選択。比較対象の初期値は全曲の最新版 |
| 語彙 | 名詞・動詞・形容詞の原形別集計、表記別内訳、出現行 |
| フレーズ | 助詞・助動詞を含む連続2〜5形態素、原文一致、正規化一致を区別 |
| 過去曲比較 | 出現総数、使用曲数、比較曲数、引用行、曲名を表示 |
| 定型表現 | 編集可能な辞書と限定的な文型ルール。理由と見直しの観点を提示 |
| 意図的反復 | 同一曲内の反復を別集計。サビ反復を過去曲重複と混同しない |
| 除外 | 今回だけ無視、当該曲で許容、全体の除外語。理由を記録し解除可能 |
| 履歴と保存 | 分析条件・結果を保存。歌詞と設定をJSONで書き出し・再取込 |

外部AIによる文脈評価・言い換え、意味の類似、グラフはMVPの次段階。MVPの改善支援は辞書に登録した方向性の表示までとする。追加開発でPC内Ollamaによる言い換えと行単位の意味類似検索（試用）を実装した。各機能の範囲と未完了事項は以下に記載する。

## 3. 画面と操作

1. ライブラリ：登録・検索・改訂履歴・比較対象選択。
2. エディター：曲名、テーマ、歌詞、分析ボタン。分析は保存と独立。
3. 結果：原文を行番号付きで表示し、指摘カードから該当行を参照。カードには該当語句、根拠、使用曲数、引用行、ルール理由、除外操作を配置。
4. 設定：閾値、除外語、表現辞書、バックアップ。

例：「ほどけていく」— 過去4/18曲、計7回／定型表現辞書にも該当。「何が、どのように変化したかを具体的な動作・物で表現する」という見直しの観点を表示する。この数値は画面仕様用の架空例。

## 4. 分析手順

### 原文と正規化

原文は変更せず保存。解析用にUnicode NFKCと空白処理を行い、各解析文字から原文位置への対応表を保持する。位置はPython文字列のコードポイント単位、開始を含み終了を含まない区間とする。改行・句点・セクション境界を越えてフレーズを作らない。

独立行の `[Verse]`、`[Chorus 2]` 等をセクション情報として分離する。未知の単独ブラケット行もメタデータとして保持し、集計対象に含める設定を用意する。本文中のブラケットは一律削除しない。

日本語解析はSudachiPyと辞書を採用候補とし、分割モード・辞書版を固定して検証する。原形と正規化形を保持し、「ほどけた」「ほどけていく」は単語では原形を共有しても、フレーズでは助動詞列を保ち別集計する。英数字は別トークンとして保持し、英語の語形統一は次段階。

### 集計と重複

- 単語集計は内容語中心。フレーズ生成は除外語を取り除く前の連続トークン列で行い、助詞を落として不自然につながった語句を生成しない。
- 内容語を含む2〜5形態素を候補とする。長さ6文字以上の原文一致も補助的に探索し、形態素分割で切れた長い表現を拾う。閾値は設定可能。
- 各候補について生の出現回数、同一行反復をまとめた回数、出現曲数を保持。曲数は曲IDを重複排除し、改訂数を数えない。
- 編集中の曲IDは比較対象から除外。別曲として登録した同一歌詞は内容ハッシュで注意表示し、削除や統合は自動で行わない。
- 長い一致に含まれる短い一致はカードをまとめるが、単語統計は保持する。

### 初期閾値と優先順位

初期値は調整前の仮説とする。比較曲数N、該当する過去曲数dfとして、Nが10以上の場合はdfが3以上かつdf/Nが20%以上で過去曲頻出を通知する。Nが10未満ならdfが2以上を参考情報として表示し、母数が少ないことを添える。単語のみの指摘は参考表示、フレーズを主な警告対象とする。

定型表現は登録ルール一致で表示し、辞書ID・一致種別・説明を根拠とする。抽象名詞＋消失動詞などの文型は「文型候補」と表示し、具体性を断定しない。初期辞書はユーザーの問題意識に沿った手作業の小規模辞書とし、一般的なAI歌詞全体の統計とは扱わない。

表示順は「過去曲頻出かつ辞書一致 → 過去曲頻出 → 辞書一致 → 単語参考」。同群ではdf降順、一致長降順、出現位置順。同曲内のサビ反復だけでは過去曲頻出にしない。意図的に繰り返す行も生の回数では確認できる。

## 5. データ構造

IDはUUID文字列、日時はUTC、画面では利用者の時間帯に変換。SQLiteの外部キーを有効化する。

| テーブル | 主な列・制約 |
| --- | --- |
| songs | id PK, title, theme, created_at, updated_at |
| song_revisions | id PK, song_id FK, revision_number, lyrics_raw, content_hash, created_at。UNIQUE(song_id, revision_number) |
| tags / song_tags | タグと曲の多対多。song_tagsの複合PKで重複防止 |
| sections | id PK, revision_id FK, label, start_offset, end_offset |
| tokens | revision_id FK, ordinal, surface, lemma, normalized, pos, reading, start_offset, end_offset。複合PK(revision_id, ordinal) |
| expression_rules | id PK, kind, pattern_json, reason, review_hint, enabled, version |
| analysis_runs | id PK, target_revision_id nullable FK, input_snapshot, input_hash, corpus_snapshot_json, settings_json, analyzer_version, dictionary_version, created_at |
| findings | id PK, run_id FK, kind, start_offset, end_offset, expression, evidence_json, priority |
| exclusions | id PK, scope, song_id nullable FK, expression_key, finding_kind, reason, enabled |
| schema_migrations | version PK, applied_at |

corpus_snapshot_jsonには比較した曲ID・改訂ID・内容ハッシュを保存。evidence_jsonには該当曲ID、改訂ID、引用文、位置、集計数とルール版を保存し、後の編集で過去結果が変わらないようにする。未保存入力はinput_snapshotだけで分析可能。

歌詞変更時は新改訂を作り、トークンを再生成。設定や辞書変更時はキャッシュキーを変更。削除は曲・改訂・トークンを一つのトランザクションで削除し、関連する分析履歴も削除対象として事前に件数を表示する。バックアップに残る内容は別途利用者が管理する。

索引：song_revisions(song_id, revision_number)、tokens(lemma)、findings(run_id)、song_tags(tag_id)。初期20曲ではオンデマンド集計し、実測後に集計キャッシュを追加する。

## 6. 実装構成と運用

採用案：Python、Streamlit、SQLite、SudachiPy、pytest。画面・分析・永続化を分離する。src/lyric_analyzer配下にui、analysis、storageを置き、tests、data/rules、docsを別配置する。バージョン選定は環境構築時に公式情報とWindows実機で確認し固定する。

起動はlocalhostに限定し、Windows用起動スクリプトで環境準備とアプリ起動を案内する。DBはユーザーデータ用フォルダへ保存し、Gitには歌詞、DB、バックアップ、APIキーを含めない。デモデータには自作の短文を使う。

JSON書き出しはスキーマ版付き。取込は事前検証・プレビュー・トランザクションで行い、同じIDがあれば上書きせず選択を求める。DB全体のバックアップはSQLiteのバックアップ機能を使う。

### 指摘の有用性評価の進捗集計

Issue09の10〜20曲レビューの準備として、batch-analysis-1を追加。保存済み最新版1〜20曲を明示選択し、各曲を自曲以外の保存曲全体と比較する。登録日・制作日の絞り込みは行わず、未知タグの扱いを選べる。改訂・比較曲・辞書の確認と、そのスナップショットと条件に結び付いた明示確認を必須とする。選択の初期値は空で、歌詞編集・AI呼び出し・評価の自動付与は行わない。

全曲を計算してからBEGIN IMMEDIATEで曲・辞書のスナップショットを再照合し、全履歴・比較元リンクを一括保存する。途中失敗・不正な対象・変更検出なら全件未保存。既存の履歴・評価を維持し、新しい未評価の分析を追加する。保存時の全体・曲単位の有効な除外を既存の履歴保存方式で記録する。実行中は直近50条件の重複追加を抑制。結果から既存評価フォームへ移動できる。DB版7を維持する。

finding-review-progress-1は保存済みの上位最大10対象と最新のfinding_reviewsを照合する。評価画面と共通のreview_candidatesを使い、report-1は出現単位、report-2は文法的参考情報を除いた表現単位の先頭10件。同じDBスナップショットから履歴メタデータと対象指摘・ラベルだけを取得し、比較元の歌詞全文や評価メモは集計しない。対象外の指摘への評価は集計に含めない。

評価方式を分離し、既定では曲IDごとの最新分析を採用。未保存入力は本文ハッシュで区別する。同時刻は分析IDで順序を固定し、新しい未評価の分析へ古い評価を持ち越さない。全履歴集計も可能だが、保存曲数と分析件数を区別する。有用率は有用合計／評価済み合計、未評価を除外、分母0はnull。指摘なしは評価完了に含めない。条件や辞書の異なる分析も含み得るため、精度や合格は断定しない。

未評価の履歴を絞り込んで既存の評価フォームへ移動し、保存し直した最新評価を集計する。CSV・JSONは曲名・歌詞・指摘本文・評価メモを除き、件数と履歴・曲・入力の識別子、版を保持する。確認用書き出しの取り込みは対象外。DB版7を維持し、AIは呼び出さない。

### 制作日の保存と期間別集計

DB移行7でsongs.composed_onを追加。日単位のYYYY-MM-DDまたは空文字（不明）を保存する。登録日時・改訂日時と独立し、既存曲・見出し付きファイルからの取り込みは不明のまま。制作日は手動入力し、日付だけの変更で歌詞改訂を増やさない。楽曲JSON形式1に任意フィールドとして追加し、省略時は不明。全データバックアップはDB版5〜7を受け付け、不足する制作日は不明として移行する。現在のDB版は7で、以下の版6の記載は各機能を追加した当時の値である。

vocabulary-trends-1は保存済み各曲の最新版を対象に、原形単語・原文／NFKCフレーズの月別または年別の使用を比較する。制作日がある曲だけを期間別分母に含め、不明曲数と引用は別表示。対象曲の存在する期間のみ表示し、選択表現がない期間は使用数0、割合0とする。使用曲数／対象曲数、反復込み出現回数、曲ごとの異なる本文行数を区別する。異なる曲IDは同じ本文でも別曲。単語は品詞別、フレーズは4文字以上で、文法的参考情報の切り替えを用意する。

入力条件・対象スナップショット・制作日を保持し、編集後は再集計を促す。表示は使用曲数順で先頭200表現から選べ、絞り込みで対象を変えられる。引用は先頭200箇所を表示し、JSONには不明日付の曲を含む全根拠と位置・改訂・ハッシュ・制作日を出力する。CSVは選択表現の期間別数値。集計結果はセッション内のみで、確認用書き出しの取り込みは対象外。AI呼び出しは行わない。制作日の精度指定・実歌詞の有用性評価は別途検討する。

制作日の一括編集は検索・不明日付条件で読み込んだ最大2,000曲を対象に、固定行数の一覧で変更後の日付だけを編集する。曲ID・曲名・元日付の対応を検証し、変更前後を表示、変更内容に結び付いた確認後だけ保存。再読み込みは未保存の一覧編集を破棄する。BEGIN IMMEDIATE内で全対象のID・曲名・元日付・更新日時を再照合し、競合・削除・不正値・途中失敗なら全件取り消す。制作日と更新日時だけを更新し、歌詞・改訂・Styles等を維持。DB版7を維持する。成功時は選択中の曲の制作日欄も更新し、期間別集計には再実行を促す。

### 意味の近い行の検索（試用）

semantic-lines-1は総合分析保存時の対象本文1行と、利用者が選択した比較曲の本文行を比較する。比較曲の初期選択は空。自曲・タグ・空行を除き、原文前後の空白を除いた同一行をまとめる。引用は保存時の曲ID・改訂ID・行番号・原文範囲を保持し、繰り返し箇所も残す。NFKC表記統一で対象行と同じ行の除外は任意。編集後の歌詞を使うには総合分析の再保存が必要。

固定ループバックのOllama /api/embedとembeddinggemma:300mだけを使用。sentence similarity用の接頭辞を両側に付け、truncate:false、8行ずつ数値化する。ベクトルは有限数・非ゼロ・2〜4096次元を検証し、正規化してコサイン類似度を計算する。途中の次元変化・件数不一致を拒否する。引用は生成せず、解析時の原文位置から構成する。近さの下限と最大20件の表示を選べるが、初期下限0.75は未検証の試用値である。

1行1,000文字、比較元は反復込み20,000行・異なる本文6,000種類が上限。待ち時間は1要求45秒、応答1MiBまで。クラウド属性・未対応名のモデルを拒否し、モデル情報とdigestを実行前後・各未キャッシュ要求前に照合する。メモリー内キャッシュはモデル識別値・本文・解析版をキーに最大800バッチ。保存先にベクトルを書き込まない。アプリはモデルを自動取得しない。

全入力JSONの事前確認と、対象行・比較曲・モデル・条件に結び付いた明示確認を必須とする。モデル確認だけでは歌詞を渡さない。失敗時は基本分析と前回結果を保持する。数値は意味一致確率ではなく、人物・時制・否定が違う行も高くなるため語の差を補助表示する。自作6例の確認は実歌詞の有用性や精度の証明としない。

結果はセッション内だけ保持し、semantic-lines-1のJSONに対象引用・過去曲の根拠・曲と改訂識別子・本文ハッシュ・モデルdigest・条件を出力する。DB版6は維持し、総合分析JSON・全データバックアップへの格納と結果JSONの復元は対象外。Issue12は実歌詞での評価・閾値検証・制作時期別傾向を未完了のまま継続する。

### ライブラリ全体の語句集計（意味類似とは別の機能）

library-vocabulary-1として、各曲の最新版の原形単語／原文フレーズ／NFKCフレーズを集計する。使用曲数は曲IDを重複排除し、出現回数は原文範囲を保持する。異なる本文行数は(song_id,line_text)で数える。内容語と汎用語の方針は総合分析の参考情報に合わせ、汎用表現を含める選択も提供する。フレーズは2〜5形態素で、意味類似や長文近似の探索は対象外。

使用曲数・フレーズ文字数・登録日（日本時間）で絞り、上位50種類の一覧から使用曲と原文行へ移動できる。引用は選択曲の先頭200箇所まで。期間は登録日であり制作日を推定しない。保存内容の変更後も、集計し直すまでは旧スナップショットを表示する。CSV・JSONは一致する全種類の語句と統計だけを持つ。集計は実行中のセッションと最大3件の結果キャッシュで保持し、DB版6を維持する。辞書・解析器・集計方式の版をキャッシュキーとJSONに含める。

候補は意味を保つ案、具体的な情景へ変える案、視点を変える案に分ける。採用は手動。タイムアウト・制限超過時もローカル分析結果を残す。提供元・モデル・プロンプト版を分析履歴に保存する。

## 9. MVP検証セット

- 同じサビを3回：生の回数3、使用曲数1、過去曲がなければ過去曲警告なし。
- 過去3/10曲に「ほどけていく」：過去曲頻出、辞書有効なら両軸の根拠を表示。
- 自曲の旧改訂にだけ一致：比較曲数にも重複曲数にも加算しない。
- 「君」「僕」だけ頻出：単語参考として表示し、フレーズの強い警告にしない。
- タグだけ一致：歌詞重複として数えない。行をまたぐ人工的フレーズも生成しない。
- 活用違い：単語原形は合算し、異なるフレーズ形は内訳を残す。
- 辞書一致のみ：AI生成とは断定せず、登録ルール由来の指摘として表示。
- 編集・削除・再取込：古い集計が新しい分析に混ざらず、失敗時に半端な保存が残らない。

初期性能目標：20曲×各2,000文字、解析器初期化後の新規分析で5秒以内。Windows実機のCPU・メモリ、初回時間と再実行時間を併記し、未計測の段階で達成済みとは扱わない。

評価用に自作短文30件以上を用意し、完全一致・正規化・境界処理の正解を固定する。実歌詞の指摘は「有用／意図的／誤検出」で人が評価する。暫定的に上位10件の有用率70%以上を目標とし、利用者の判断を記録して調整する。
